The gap nobody names

The preview is unsigned. The capture is signed. Nothing links them.

Camera / SBI device
unsigned preview →
Liveness check passes on face A
signed capture →
Registration packet stores face B
  • Capture swap: whoever controls the preview can pass liveness with one face and enrol another.
  • Android: the client never sees preview frames at all; the device app shows the stream and returns only the signed capture.
  • Injected video (OBS, deepfake pipelines) is outside ISO/IEC 30107. Insiders can log in with a supervisor's photo.
  • No audit trail: a client-side pass/fail cannot be re-checked by the server later or re-scored with a better model.

What is different

Each idea is built and tested. None is claimed beyond what the claim sheet allows.

Capture binding

Four locks before any accept: nonce echoed in the device-signed capture, frame hash chain, identity continuity, time. Works on unmodified SBI.

Evidence, not a verdict

A signed JWS in the face BIR. One command re-verifies it; a newer model can re-score stored crops. Merkle transparency log.

Cues that fail differently

Passive, moiré, flash reflection (20.7-bit random colour code; author-tested on 1 setup), scene, stereo. Each abstains when the station lacks hardware.

Injection defence

Device identity chain, OS camera registrations (OBS found via DirectShow), JPEG stream fingerprint. Not a renamed-driver defence.

Inclusion by design

Blink, pulse and pupil reflex only ever vote for life. Hindi, icons, speech, accessibility profiles, infant mode, dual-control exceptions.

An SBI proposal

An optional Liveness Profile (signed preview, signed light log, signed burst) with a runnable reference device. Our own draft; not yet posted to MOSIP.

Engineering Verification & Scientific Rigour

ISO/IEC 30107-3 Clopper-Pearson confidence bounds, on-device hardware benchmarks, honest threat disclosure.

Verified on Hardware & Code

  • 738 automated tests pass (0 failures, strict CI on Linux & Windows)
  • Hardware measured: Models and camera timed on one phone; OBS veto shown on a Windows webcam list
  • Flash challenge: 1,679,616 sequences = 20.7 bits (≤ 3 changes/sec, WCAG 2.3.1 compliant)
  • Capture binding: 4 cryptographic locks; capture-swap attack blocked by construction
  • Insider threat analytics: 6 in 40 at 2% baseline yields z ≈ 5.87; operator self-enrollment blocked
  • Audit trail: Merkle transparency log matching Certificate Transparency test vectors

Scientific Discipline & Limits

  • Statistically honest: Avoids pseudo-claims on small lab sets; ISO/IEC 30107-3 harness ready for field calibration
  • Scaffold, not full Client: Evaluation scaffold; no live session on certified SBI device yet
  • Android replay limit: Passive model fooled by screen replay (0.98 score) & flash needs ≥ 3 fps (phone got 2.7–2.9 fps); replay defence on Android rests on challenge alone
  • Inclusive UX: Native Devanagari Hindi verified; accessibility profiles for elderly & disabled residents
  • Red team findings: Automated genetic fuzzer discovered moiré blind spots; resolved via flash/stereo fusion voting

Self-Red-Teaming. On synthetic screen replays with the passive model assumed fooled and no flash light, the fusion accepted 4 of 85 display pitches; with the flash cue, 0. Logged as R-03 with R-01 (moiré blind pitches); the fix (an accept needs a flash or stereo vote, else a challenge) is enforced for operators and supervisors.
